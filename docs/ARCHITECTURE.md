# 설계 메모: DB 선택과 단계별 계획 (초안, 2026-11-09)

## 0. 범위

- **고객 범위는 2024~2026년에 결제·등록한 고객입니다.** 고객을 연도로 나눌 때는 결제일을 쓰고, 결제 전이면 등록일을 씁니다.
- 매출은 두 가지 기준으로 봅니다. **결제일 기준**은 실제로 들어온 돈이고, **교육일 기준**은 그 달에 열린 기수의 매출(결제 전 신청 포함)입니다. 전체 화면에서 바꿔 볼 수 있습니다.
- 자료는 연도로 거르지 않고, 이 범위의 기수·고객과 이어지는 자료를 담습니다.

## 1. 담아야 할 양 (jBU 공유 드라이브 조사 결과)

전체 폴더 953개 가운데 약 200개를 직접 훑어 보고, 나머지는 같은 비율로 추정했습니다.

| 항목 | 추정 |
| --- | --- |
| 이미지 뺀 파일 | 약 3,000개 (범위 2,000~3,500) |
| 글자가 들어 있는 파일 (문서·시트·슬라이드·PDF·Word·PPTX·Excel) | 약 1,600개 |
| 뽑아낸 텍스트 | 약 1,100만 자 ≈ 30MB (범위 600만~2,000만 자, 17~60MB) |
| 영상·음성 | 약 237GB (DB에 넣지 않고 드라이브 링크만 둡니다) |
| 2024~2026년 고객 데이터 (기수·참여자·결제·진도) | 신청 수천 건 수준, 몇 MB |

조사하면서 알게 된 점:

- **자료 파일 날짜는 믿기 어렵습니다.** 2026년에 공유 드라이브로 옮기면서 옛 파일까지 생성일이 2026년으로 바뀌었습니다. 그래서 연도 구분은 파일 날짜가 아니라 고객의 결제일·등록일로 합니다.
- **텍스트는 대부분 PPTX와 PDF 안에 있습니다.** 구글 문서·슬라이드는 거의 없습니다. 디자인된 PDF는 글자 순서가 뒤섞여 나와서, 레이아웃을 읽는 추출기나 OCR이 필요합니다.
- **개인정보가 섞인 파일이 있습니다.** 해피콜 통화 기록(…통화.txt), 수강생 이름이 붙은 과제 사본 등이 있습니다. DB에 넣기 전에 빼거나 가려야 합니다.
- **매출 원장은 드라이브에서 찾지 못했습니다.** 결산 시트(파운더스 2기), 분기 데이터 시트 정도만 있습니다. 실제 결제 내역이 어디에 쌓이는지(가인지캠퍼스 결제, 이벤터스, 회계 시스템 등) 확인이 필요합니다.
- **같은 이름·같은 크기의 중복 파일이 30여 개**, 출결 시트 자동 백업본이 15개쯤 있습니다.

## 2. 추천: 처음부터 Supabase로 가기

| | 구글 스프레드시트를 DB로 | Supabase (Postgres) |
| --- | --- | --- |
| 텍스트 자료 | 셀 하나에 5만 자까지라 긴 교재·PDF는 잘라 넣어야 함. 본문 검색이 느림 | 길이 제한 없음. 한글 부분 검색 인덱스(pg_trgm) 사용 |
| 운영 데이터 | 탭끼리 연결(기업↔사람↔기수)이 수식에 의존해 쉽게 깨짐 | 기업·사람·기수·결제를 키로 연결, 중복 방지 |
| 용량 | 파일당 1,000만 셀 | 무료 500MB, Pro 8GB |
| 동시 사용 | 여러 명이 동시에 쓰면 충돌·속도 저하 | 문제없음 |
| 권한 | 시트 공유 단위 | 회사 계정(@gainge.com)만 읽기·쓰기 (스키마에 포함) |
| 나중에 AI 검색 | 어려움 | pgvector로 같은 DB에서 가능 |
| 비용 | 없음 | 무료 또는 월 $25 |

**용량만 보면 무료 플랜(500MB)에도 들어갑니다.** 텍스트 30MB에 검색 인덱스를 붙여도 150MB 안팎이고, 나중에 AI 검색용 임베딩을 더해도 300MB 정도입니다. 다만 무료 플랜은 7일 동안 쓰지 않으면 일시정지되고 백업이 없습니다. 실제 운영 데이터(고객·결제)를 넣는 시점부터는 **Pro(월 $25, 8GB, 7일 백업)**를 추천합니다.

시트를 거쳐 가는 방식은 추천하지 않습니다. 시트에 맞춰 만든 구조를 나중에 다시 옮겨야 해서 같은 일을 두 번 하게 됩니다. 시트는 지금처럼 **입력 창구**(구글폼 응답, 현장에서 손으로 고치는 명단)로 남기고, 동기화로 DB에 들어오게 하는 편이 안전합니다.

## 3. 데이터가 들어오는 길

```
구글폼 응답 시트 ─┐
명단·출결 시트   ─┼─(Apps Script 또는 Vercel Cron, 10분~1시간마다)─► Supabase ─► 운영 데스크 화면
하열사뱅크 진도  ─┘                                                  ▲
드라이브 PPTX·PDF·문서 ──(텍스트 추출 스크립트, 하루 1번)─────────────┘
결제 내역 ──(출처 확인 후 연결)───────────────────────────────────────┘
```

## 4. 단계

1. **초안 확인** (지금): 예시 데이터로 화면 구성을 확인합니다.
2. **기반**: GitHub 저장소, Vercel 배포, Supabase 프로젝트, 회사 Google 계정 로그인.
3. **운영 데이터 이전**: 교육별 실제 정가·정원·할 일 템플릿 확정, 24~26년 기수와 참여자 명단 이관, 기업명 정리(같은 회사 다른 표기 합치기).
4. **연동**: 구글폼 응답·하열사뱅크 진도·구글챗 알림을 새 DB 기준으로 옮기기. 37기가 끝난 뒤 지금의 OKR 운영 데스크(Apps Script)를 대체합니다.
5. **자료함**: 드라이브 텍스트 추출(개인정보 걸러내기 포함)과 검색.
6. **AI 활용**: 지난 기수 자료로 질문하기, 안내문 초안 만들기.
